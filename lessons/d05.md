# Day 5. Evaluation as a gate

**Outcome:** a golden set, RAGAS scores on every run, and a CI test that fails when a change makes answers worse.

## Concept (25 min)

**Why unit tests are not enough.** Conventional tests assert one correct output for one input. An LLM system has many acceptable outputs, samples non-deterministically, and changes behaviour when the prompt, the model, the retrieved data or the provider changes. Quality becomes a property of a distribution, measured on a dataset. That dataset plus its scorers is the harness, and the harness is what lets you change anything without guessing.

**Three layers, cheapest first.**

- **Deterministic checks.** Schema valid, required fields present, action from the allowed list, no banned strings. Exact, fast, run on every case.
- **Retrieval metrics.** Recall@k and MRR from Day 4. They isolate the memory layer.
- **Model-graded quality.** A judge model scores properties no rule can check.

**How the RAGAS metrics work.**

- **Faithfulness** splits the answer into atomic claims and asks the judge whether each claim is supported by the retrieved context. The score is the supported fraction. It measures grounding, not correctness: a faithful answer built on the wrong context is still wrong.
- **Response relevancy** has the judge generate the questions the answer appears to address, embeds them, and compares them with the original question. It penalises answers that drift off topic.
- **Context recall** checks how many claims in your reference answer can be attributed to the retrieved context. It measures whether retrieval brought what the right answer needed.

**Judges are models, with model failure modes.** They prefer longer answers, favour the first option shown, and favour text like their own. Pin the judge model and version. Use temperature 0. Calibrate it: hand-label a sample and measure agreement. A local 7B judge is weaker than a frontier one; the hand check tells you by how much.

**Statistics, briefly.** Thirty cases is small. A metric of 0.80 on 30 cases has a wide confidence interval, and a 0.03 change can be noise. Treat thresholds as tripwires for large regressions, grow the set over time, and re-run a suspicious result before acting on it.

**The gate.** Thresholds in CI, set a little below the measured baseline. A change that drops the numbers does not merge. Break something on purpose and watch the gate fail, or you do not know it works.

## Lab (90 min)

```bash
uv add ragas pytest
```

### 1. Golden set

`data/golden.jsonl`: 30 cases, each with `question`, `reference` (the correct triage), and `expected_severity`. Write 10 yourself from real experience, anonymised. Let Claude Code draft 20 and you correct them. The 10 you write are the ones that matter.

### 2. Eval runner

`app/eval_answers.py`:

- Runs the graph on every golden case.
- Collects `user_input`, `response`, `retrieved_contexts`, `reference`.
- Scores with RAGAS: `Faithfulness`, `ResponseRelevancy`, `LLMContextRecall`. Use `qwen2.5:7b` through Ollama as the judge LLM and BGE as the embedding model.
- Adds a deterministic severity-match rate.
- Writes `reports/eval-<timestamp>.json`.

### 3. The gate

`tests/test_quality.py`:

```python
def test_quality_gate():
    r = run_eval()
    assert r["faithfulness"] >= 0.80
    assert r["severity_match"] >= 0.75
```

Set thresholds 0.03 below today's baseline. Then break something on purpose (drop the recall node) and watch the test fail.

## Drill

"How do you know an AI feature is safe to ship?"

Answer shape: the eval harness as the release gate. Deterministic checks, retrieval metrics, a pinned judge, thresholds in CI, human spot-checks. A change that drops the numbers does not merge.
