# Day 5. Evaluation as a gate

**Outcome:** the answer-quality eval gate is a harness component that any app plugs into, FindyFixy is its first consumer, and a change that affects answers cannot merge to `main` without a passing gate.

## Concept (25 min)

**Why unit tests are not enough.** Conventional tests assert one correct output for one input. An LLM system has many acceptable outputs, samples non-deterministically, and changes behaviour when the prompt, the model, the retrieved data or the provider changes. Quality becomes a property of a distribution, measured on a dataset. That dataset plus its scorers is the eval harness, and it is what lets you change anything without guessing.

**Three layers, cheapest first.**

- **Deterministic checks.** Schema valid, required fields present, labels such as severity matched exactly. Fast, run on every case.
- **Retrieval metrics.** Recall@k and MRR (mean reciprocal rank) from Day 4. They isolate the memory layer.
- **Model-graded quality.** A judge model scores properties no rule can check.

**The model-graded metrics.** The first three follow the RAGAS (Retrieval-Augmented Generation Assessment) definitions, written in the harness. The `ragas` package itself was rejected: it carried an advisory with no fix.

- **Faithfulness** splits the answer into atomic claims and asks the judge whether each claim is supported by the retrieved context. The score is the supported fraction. It measures grounding, not correctness.
- **Response relevancy** has the judge generate the questions the answer appears to address, embeds them, and compares them with the original question. It penalises answers that drift off topic.
- **Context recall** checks how many claims in the reference answer can be attributed to the retrieved context. It measures whether retrieval brought what the right answer needed.
- **Action quality** asks the judge whether the proposed first action would help, given the reference cause and fix. Advice cannot be "supported by context" like a fact, so faithfulness would score it low by construction.

**Judges are models, with model failure modes.** They prefer longer answers, favour the first option shown, and favour text like their own. Pin the judge model and its digest. Use temperature 0. Calibrate it: hand-label a sample and measure agreement. A failed judge call is excluded and counted, never scored 0, or judge flakiness looks like an answer regression.

**Statistics, briefly.** 30 cases is small. One case moves a rate by about 3 points. Seeded bootstrap 95% intervals show how much a mean moves under resampling. The gate fails on a floor (baseline mean minus 0.05) or on a regression outside the interval, so noise alone does not fail it.

**Why the gate is a harness component.** A gate wired to one app's types cannot be reused or shipped. The harness defines one interface, a system under test, and owns the judge, the metrics, the statistics, the reports, the baseline and the gate. The app supplies its cases and answers its questions. The dependency points one way: the app imports the harness, never the reverse.

**How the gate guards main without a GPU.** A live run is 30 cases times about 10 judge calls on a 4B and a 7B model. On a CPU-only CI runner that takes hours. So the gate runs on the developer's machine and writes an attestation: a fingerprint of every file that changes answers, the report hash and the verdict. CI recomputes the fingerprint and fails a PR whose answer-affecting files have no matching passing attestation. This is a process control, not a security control: CI trusts the local run. At scale a GPU runner replaces the attestation with a real run.

## Build

Starting point: the gate was first built inside FindyFixy (`code/app/`, commit `1e7f27a`). Its baseline is frozen in `code/evals/baseline.json` from report `eval-20261027T044126Z`. These steps move it into the harness without changing a score.

### Target layout

```
code/
  harness/                 the product. Never imports app.
    eval/
      case.py              Case: id, group, question, reference, expected labels
      sut.py               SystemUnderTest: describe() -> dict, answer(case) -> Answer
                           Answer: text, contexts, action, labels, meta
      judge.py             the judge seam, moved unchanged
      metrics.py           the 4 metrics, moved unchanged
      stats.py             bootstrap and aggregation, label match generalised
      report.py            report files, baseline, comparability, gate
      provenance.py        judge digest, prompt hashes, dataset hash, git, plus describe()
      events.py            the harness event vocabulary, sent to an injected callback
      attest.py            fingerprint of answer-affecting files, attestation file, verify (stdlib only, runs in CI without installs)
      runner.py            run_eval over a SystemUnderTest
      cli.py               run, gate (writes the attestation on a full pass), freeze, show-case
  app/
    golden.py              stays: builds the cases from the corpus
    eval_adapter.py        FindyFixy as a SystemUnderTest: holdout recall, graph, severity label, twin data
    eval_answers.py        thin entry point: builds the adapter, calls harness.eval.cli
    console_eval.py        the console's Eval run: bridges harness events into the live stream
```

What already works unchanged: the judge, the metrics, bootstrap and aggregation, report files, the baseline and the gate. They take strings and numbers. What stays in the app: the golden-set builder, the holdout recall, the severity label, the twin group and the graph wiring.

## Drill

"How do you know an AI feature is safe to ship?"

Answer shape: the eval harness as the release gate. Deterministic checks, retrieval metrics, a pinned and calibrated judge, a baseline with confidence intervals, a merge rule on `main`, human spot-checks. A change that drops the numbers does not merge.

### Where the time goes

About 10.2 judge calls per case: 1 to split claims, 4.77 claim verdicts, 1 for relevancy, 2.47 recall verdicts, 1 for action. The answer is about 6 s of the roughly 28 s per case. `ollama ps` mid-run showed only the 7B judge loaded, so the two models appear to swap in GPU memory each case (not timed separately).

### Batched judge verdicts: rejected

Re-judging the saved per-item verdicts of the attested run with one batched call per case (`qwen2.5:7b`, temperature 0):

| Metric | Items | Agreement | Cohen's kappa | Mean case shift | Malformed batches |
|---|---|---|---|---|---|
| faithfulness | 143 claims | 0.839 | 0.52 | +0.008 | 0 |
| context recall | 72 of 74 sentences | 0.917 | 0.53 | -0.059 | 1 |

The bar set before the run was 0.9 agreement and a mean shift inside the 95% interval. Faithfulness failed on agreement (0.839). Context recall met both bars: 0.917 agreement, and the mean moved from 0.928 to 0.869, inside its interval of 0.856 to 0.983. The malformed batch (2 sentences) was excluded from the comparison; in a live run it would be a failed metric. Faithfulness was the change under test and it failed, so one judge call per item stays for both metrics. Batching context recall alone would save about 1.5 calls per case and is left untried. The experiment script and its output are not committed. Limit: compared with one per-item run, not per-item against itself (per-item means moved less than 0.003 between reruns on 2026-10-26).
