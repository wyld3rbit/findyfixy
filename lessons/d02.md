# Day 2. Structured output and tools

**Outcome:** the agent emits schema-validated triage records and calls tools. You measure what MCP costs against a direct API call.

## Concept (25 min)

**Structured output is the contract** between a probabilistic component and a deterministic system. Free text cannot be routed, tested or audited. A schema turns each answer into a record with typed fields, and every downstream decision reads fields, not prose.

**Three ways to get it, in rising order of reliability.**

- **Prompt and parse.** Ask for JSON, parse the reply. Fails on stray prose, trailing commas, truncation.
- **JSON mode.** The runtime guarantees syntactically valid JSON. It does not guarantee your shape.
- **Constrained decoding.** The runtime compiles your JSON Schema into a grammar and masks every token that would break it during sampling. Ollama does this when you pass a schema. Shape is guaranteed: keys, types, enums.

Constrained decoding guarantees syntax, not meaning. You saw this on Day 1: the schema said a number, the model wrote 75 on a 0 to 1 field, and nothing stopped it. Numeric bounds and cross-field rules are not reliably enforced by the grammar. So validate semantics in code (Pydantic), feed the validation error back once, then escalate. Bound the retries, or a stubborn model becomes a cost leak.

**Enums are routing.** A `Literal["sev1", "sev2", "sev3", "sev4"]` field is a routing key. Free-text severity is a classification problem you pushed downstream.

**Tool calling.** The model never executes anything. It emits a structured request: a tool name and arguments. Your code validates the arguments, executes the call, and appends the result to the context. The loop repeats until the model answers. The arguments are untrusted input from a model that has read untrusted text. Validate them like any request from the internet. The model never holds credentials; your code does (Day 7).

**MCP.** The Model Context Protocol is JSON-RPC between a client (the agent host) and a server (the tool provider). The client calls `tools/list` to discover tools and `tools/call` to invoke one, over stdio or HTTP. Its value is reuse: one server, many clients, a shared ecosystem.

Its costs are concrete. Every tool's name, description and JSON Schema is placed in the model's context on every turn, so input tokens grow with the number of tools exposed. Tool-selection accuracy also drops as the list grows. A server hop adds latency and another process to run, patch and authenticate.

**The rule you can defend.** MCP where cross-client reuse matters and the tool set is small. Direct function binding on hot paths, exposing only the tool that node needs. Decide by measured tokens and latency per call, which is today's lab.

## Lab (90 min)

### 1. Triage schema

```python
from pydantic import BaseModel, Field
from typing import Literal

class Triage(BaseModel):
    severity: Literal["sev1", "sev2", "sev3", "sev4"]
    component: str = Field(description="service or subsystem most likely at fault")
    next_action: str = Field(description="one concrete first step")
    confidence: float = Field(ge=0, le=1)
```

Swap Day 1's schema for `Triage`. Add a validation-retry: on `ValidationError`, re-ask once with the error text, then escalate.

In the repo, the model call returns raw text. Ollama gets the schema through `format=` (constrained decoding), and Pydantic validates the text in your code. So the retry prompt carries Pydantic's own error text and the bad reply. The worst case is 2 calls per model. If the small model is still invalid after its retry, escalate. If the large model is, raise an error. The Day 1 answer with `confidence: 75` now fails validation, retries, and escalates.

### 2. Two tools, two ways

Build a fake `get_recent_deploys(service, hours)` that returns JSON from a local file.

- **Direct:** bind it with `llm.bind_tools([get_recent_deploys])` in a LangGraph `ToolNode`.
- **MCP:** wrap the same function in a minimal MCP server (`uv add mcp langchain-mcp-adapters`, FastMCP over stdio) and connect with `langchain-mcp-adapters`. Ask Claude Code to scaffold both.

Run the tool loop as its own step before the Triage call: the model asks, `ToolNode` runs the tool, repeat, with a cap of 4 turns. When tested, a model call with `format=` set returned no tool calls, so tools and the Triage schema cannot share one call. The tool's results then go into the Triage prompt as evidence, with the arguments shown.

Build the MCP server's argument schema from the same fields as the direct tool. If the wording or bounds differ, the token comparison measures that and not MCP.

The adapter's tools are async-only, so run the graph with `ainvoke`. The adapter's default opens a new session on every tool call, which over stdio starts a new server process each time. Measure that default, and also one persistent session held open for the whole run.

### 3. Measure

For 10 runs of each of three paths, log input tokens, output tokens and wall time: direct, MCP with one persistent session, and MCP with a new session per call. Run one warm-up call first and leave it out, because the first call after a model load is slow. Use one fixed question that needs the tool, such as "Which deploys to the auth service happened in the last 24 hours?". Put the result in the Results section below as a table.

In the repo: `uv run python -m app.direct_run`, `uv run python -m app.mcp_run session` and `uv run python -m app.mcp_run per-call`.

### The overhead MCP added in this setup

- Tokens: 0 input tokens. Every run on every path sent 499. Output tokens differ by under 1 on average (sampling noise).
- Time, persistent session: about 0.00s at the median (0.57 vs 0.57). The mean is 0.012s higher, from two runs at 0.65s and 0.61s that also generated more tokens (53 and 49).
- Time, new session per call: +0.57s per run, one call per run (1.14 vs 0.57). That is about the same as the server startup measured on its own (0.46s to 0.58s). So the cost is the process start, paid again on every call.

### What the numbers show

- The schema the model sees is the same on both paths (a test compares them), so the token count does not move. With one tool, MCP adds no input tokens. The lesson says MCP token cost grows with the number of tools exposed, so one tool understates it.
- A persistent session costs almost nothing in time. The default (a new session per call) doubled the time per run here. For a tool called on every request, that is a large fixed cost.
- The model called the tool in 30 of 30 runs and gave the right answer in 0 of 30. In every run its arguments were `hours=1,service=auth`, a 1 hour window for a 24 hour question. The arguments are legal (hours 1 is inside the schema's 1 to 168), so validation passed, and the tool correctly returned nothing. Schema validation checks shape, not meaning.
- The runs are near identical: this model repeated itself almost exactly. Ten runs show one behaviour, not a spread, so they say nothing about variance.
