# Day 1. Setup and first graph

**Outcome:** a LangGraph agent that answers with a small local model first and escalates to a larger local model only when the small answer is weak.

## Concept (25 min)

**Model cascades.** A cascade sends every request to the cheapest model first and escalates only when a signal says the answer is weak. Expected cost per request is `c_small + p_escalate × c_large`. Expected latency on the escalated path is the sum of both calls, because you pay the small call before you know you need the large one. The cascade wins when `p_escalate` is low and the small model's kept answers meet the quality bar. It loses when most traffic escalates: you then pay for two calls and get the latency of both.

**Two error types, unequal cost.** A false keep returns a bad small-model answer to the user. That is a quality incident. A false escalate sends an easy question to the large model. That is wasted spend and latency. The threshold trades one for the other. Choosing it is a business decision, and it needs both rates measured on a labelled set (Day 5). A threshold picked by feel is a guess about a ratio you have not measured.

**The escalation signal is the hard part.** Options, cheapest first:

- **Verbalised confidence.** The model writes a number. It is cheap and poorly calibrated. Small models overstate it and drift between scales. Treat it as a weak prior.
- **Rule checks.** Schema complete, required fields present, an action from the allowed list. Deterministic and cheap. They catch malformed answers, not wrong ones.
- **Retrieval score.** If memory found no close prior incident, the question is novel. Novel questions are where small models fail (Day 4).
- **Self-consistency.** Ask k times and measure agreement. Stronger signal, k times the cost.
- **A judge model.** A second model grades the first. Strongest of these, and it costs an extra call per request.

Production routers combine several. Today you start with the weakest one on purpose, so you can measure how weak it is.

**Why a graph.** An agent is a state machine. State is a typed record passed between steps. Nodes are functions that read state and return a partial update. Edges decide what runs next. A conditional edge is a function of state that returns the next node's name. LangGraph merges each node's update into state (overwrite by default; reducers such as append are declared per field), validates the graph at `compile()`, and can checkpoint state after every step.

Three properties follow, and each matters later. Nodes are pure functions of state, so you test them with fakes and no model. Control flow lives in edges, not buried in `if` statements inside nodes, so it can be read, drawn and changed in one place. Checkpointing per step gives you retries, pause and resume, and human approval gates (Day 9).

**What changes at scale.** More tiers in the cascade. Thresholds per tenant or per intent. Warm model pools, because a cold load of a 7B model adds seconds to the first escalation. Escalation rate becomes a top-line operational metric: when it rises with no traffic change, something drifted.

### 4. The router graph

Ask Claude Code to build `app/graph.py` with this spec:

- State: `question`, `answer`, `confidence` (0 to 1), `model_used`.
- Node `small`: `ChatOllama(model="qwen2.5:1.5b")` with structured output `{answer: str, confidence: float}`.
- Conditional edge: if `confidence >= 0.7` go to END, else go to `large`.
- Node `large`: `ChatOllama(model="qwen2.5:7b")`, same schema.
- Model names come from `.env` (`SMALL_MODEL`, `LARGE_MODEL`) so they can be swapped later.
- `main()` runs 5 sample questions and prints the model used and latency for each.

Do not clamp `confidence`. The small model writes it on whatever scale it likes (0.95, 9, 75, 100 all appeared). Record the number as written, and expect the range check to fail on some answers: that is the weakness of the signal, and Day 2 adds validation.

Skeleton for reference:

```python
from typing import TypedDict
from langgraph.graph import StateGraph, END

class S(TypedDict, total=False):
    question: str; answer: str; confidence: float; model_used: str

g = StateGraph(S)
g.add_node("small", small_node)
g.add_node("large", large_node)
g.set_entry_point("small")
g.add_conditional_edges("small", lambda s: END if s["confidence"] >= 0.7 else "large")
g.add_edge("large", END)
app = g.compile()
```

The skeleton is the minimum. In the repo the graph is built by `build_graph(ask, ...)`, which takes the model-calling function as an argument, so routing is tested with fakes and no Ollama. The router is a named function annotated `-> Literal["large", "__end__"]`. LangGraph reads that annotation to draw the edge: with a bare `str` the diagram silently drops `small -> large`, though routing still works.

### What I learned

- The model's confidence is text it writes. Ollama gives no confidence score and no range. The docs do not say whether schema minimum or maximum values are enforced.
- The small model used two scales: 0 to 1 (two answers) and 0 to 100 (three answers), though the field description said 0 to 1.
- Rescaling would not have changed routing here. 75, 90 and 95 become 0.75, 0.9 and 0.95, all above 0.7.
- The model rated itself too high. Question 1 gave an intro and no checks (scored 75). Question 4 gave no steps (scored 0.742). Question 3 called 429 a "condition code" (scored 90).
- Self-reported confidence is cheap and noisy. A better signal is needed: rules, retrieval score, a judge model, or token probabilities.
