# Day 10. Autonomy as policy

**Outcome:** the last transition of `code/docs/strategy.md`. The level each class of action runs at is set by measured evidence in code, and a regression lowers it without a human decision. The last invariant moves to built. The whole system starts from a fresh clone with one command, a one-to-two-page vision projects the strategy forward, and a short live demo shows the system handling failure as well as success.

## Concept (15 min)

**Autonomy is earned per action class.** An agent is not trusted or untrusted as a whole: each class of action runs at its own level, set from evidence, as `code/docs/design.md` ("Autonomy as policy") describes. The engineering point is the last rule. No setting can raise a level by hand, because a level that can be set by hand is a preference, not a control.

**Reproducibility is the first test of a system.** A demo that runs only on its author's machine proves the machine. A fresh clone with pinned dependencies, pinned images, no hidden state and no absolute paths proves the system. Readers assume the worst about anything they cannot run.

**A vision is the strategy, extrapolated.** It describes how the system and its controls look two to three years out if the strategy holds: concrete, grounded in what was measured, optimistic and not audacious, and one to two pages long. It assumes realistic resources, and it is judged later by comparing it with what was actually built.

**A credible demo shows failure handled.** Routine questions answered cheaply are expected. The escalation, the approval pause and the blocked injection are what show the system was engineered.

## Build

### 1. Autonomy policy

A harness component holds one level per action class and the thresholds for each move, set from the numbers measured on Days 7 to 9. It reads the evidence (gate results, injection results, the approval record) and outputs the level; the approval port from Day 9 applies it. A test changes the evidence and sees the level change, and a test proves no configuration can raise a level directly.

### 2. One command from a fresh clone

`make setup` and `make demo` from a fresh clone in a new folder. The open decision on the board ("One-command bootstrap") is settled first: how a missing Ollama is handled without a hidden system install. If the clone does not run the first time, that is fixed before anything else.

### 3. Demo incidents

A script fires 5 incidents in order: a routine one on the small model, one with a near-duplicate in memory, a hard one that escalates on the computed signal, one that needs a rollback and pauses for approval, and a poisoned one that policy blocks.

### 4. Vision and strategy review

`code/docs/vision.md`, one to two pages, linked from the README. The strategy's review section records how each policy held across Days 7 to 10, and every enforcement row is built or explicitly deferred with its reason.

### 5. Show and tell

A 3-minute script and 6 slides: the problem in one relative number, the two planes, three decisions with their trade-offs, the results table, the stack in one line each, and what breaks at 100 times the load. The demo is recorded once as a backup.

### 6. Visualizer and artifacts

The architecture page shows every box built or explicitly deferred. ADR 0011 records the phase and reports against the strategy. READMEs, CHANGELOG, tracker and ADR snapshot updated in the same commits.
