# Day 3. Memory I: ingestion

**Outcome:** a corpus of 200 past incidents, chunked, embedded and stored in Postgres with pgvector, refreshed by a re-runnable ingestion job.

## Concept (25 min)

**Why retrieval.** A model knows what was in its training data. It does not know your services, your past incidents or your fixes. Retrieval-augmented generation finds the relevant records at request time and places them in the prompt. For triage this is the highest-leverage context there is: most incidents rhyme with an earlier one, and the earlier root cause and fix are the best hint the model can get.

**Embeddings.** An embedding model (a bi-encoder) maps a piece of text to a fixed-length vector. Texts with similar meaning land near each other. Similarity is measured by cosine. If you normalise vectors to unit length, cosine equals the dot product, which is cheaper and what indexes optimise for. `BAAI/bge-small-en-v1.5` produces 384 dimensions and runs on a laptop.

Three constraints follow. Queries and documents must be embedded by the same model. Changing the model means re-embedding everything, so store a model version on every row. Dimensions cost memory and index time linearly, so a larger model has to earn its keep in measured recall.

**Chunking sets the unit of retrieval.** Too large, and one vector averages several topics, so it matches nothing well and wastes context when retrieved. Too small, and a chunk loses the context that made it useful. Postmortems have natural structure (summary, timeline, root cause, remediation), and structure-aware chunks beat fixed token windows on documents like these.

**Metadata does more than people expect.** Service, severity and date let you filter before similarity search. A filter on `service = auth` removes most of the noise that embedding tweaks try to fix.

**Ingestion is a data pipeline, with data pipeline rules.** Source, clean, chunk, embed, upsert. Make it idempotent with a content hash per chunk, so a re-run writes only what changed. Handle deletes, or the index serves incidents that were retracted. Version the embedding model so a migration can run side by side.

**The index.** Exact nearest-neighbour search compares the query with every vector: correct, and linear in corpus size. HNSW is approximate. It builds a layered graph, enters at a sparse top layer and walks greedily toward the query through denser layers. Search cost grows roughly logarithmically. Its knobs trade recall for speed and memory: `m` (links per node) and `ef_construction` at build time, `ef_search` at query time.

pgvector keeps vectors in Postgres beside the relational data, inside the same transactions and backups. That is the right call until vector volume or query load justifies a dedicated store.

## Lab (90 min)

### 1. Postgres with pgvector

`docker-compose.yml`:

```yaml
services:
  db:
    image: pgvector/pgvector:pg16
    environment: { POSTGRES_PASSWORD: dev, POSTGRES_DB: triage }
    ports: ["5432:5432"]
```

```bash
docker compose up -d db
uv add "psycopg[binary]" pgvector sentence-transformers
```

### 2. Synthetic corpus

Ask Claude Code to generate `data/incidents.jsonl`: 200 synthetic postmortems across 8 services, each with `id, service, severity, date, summary, timeline, root_cause, remediation`. Seed in 20 near-duplicate pairs so retrieval has something real to find. Label the file synthetic.

### 3. Ingestion job

`app/ingest.py`:

- Table: `chunks(id text primary key, incident_id text, section text, service text, severity text, body text, hash text, embedding vector(384))`.
- Chunk by section. Hash each chunk. Skip unchanged hashes.
- Embed with `SentenceTransformer("BAAI/bge-small-en-v1.5")`, normalised.
- HNSW index: `CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);`

Run it twice. The second run should write nothing.

### 4. First query

Embed "auth latency spike after certificate rotation" and return the top 5 by cosine distance with their service and section.
