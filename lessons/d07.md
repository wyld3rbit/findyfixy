# Day 7. The trust boundary

**Outcome:** the first two transitions of `code/docs/strategy.md`. The agent is tested on harder, versioned data, and escalation runs on a signal the system computes, not on the model's own confidence (policy 1). A deterministic policy stands between every proposed action and any system, and every tool call carries a short-lived token scoped to one tool and one resource. Two invariants move from planned to built: no model output acts until policy approves it, and no credential outlives one call or reaches beyond one tool.

## Concept (30 min)

**Why the self-reported signal failed.** The router escalates when the small model rates its own answer below a threshold. The strategy's diagnosis records that this number never tracked quality and never triggered escalation. A model's confidence is text it generates, shaped by the same prompt that shaped the answer. A useful escalation signal comes from facts outside the answer: how strongly retrieval supports it, whether the answer's severity agrees with the incidents it cites, whether validation needed a retry. Each is cheap, recorded and testable without a model.

**Why the data must get harder first.** The current golden set is small and mostly built around near-duplicates in memory (see the strategy's diagnosis). A router that never escalates scores well on it, so it cannot tell a better router from a worse one. Versioned data keeps the old set frozen as a regression check and adds the cases that should be hard: alerts with no precedent, conflicting signals, cascades across services, raw noisy alert text, and incidents whose remediation text carries an injected instruction.

**Why prompt injection is architectural.** A model receives one token stream. System instructions, the user's question, retrieved documents and tool results are all text in that stream, and the model has no reliable boundary between instructions to follow and data to read. Any text that reaches the context can steer it. Direct injection comes from the user; indirect injection arrives through content the agent fetched, such as a past incident's remediation note. No filter catches every phrasing, so the defence cannot depend on the model behaving. It has to bound what a misbehaving model can do.

**Controls that hold even when the model is fooled.**

- **Model output is untrusted input.** It is validated against a schema and an allow-list before anything acts on it, and never passed to a shell, a query or a URL unvalidated.
- **The model proposes; code decides.** Policy uses facts the model cannot forge: the severity from the validated record, a deploy that exists in the deploy log, the time window.
- **Least agency.** Each step sees only the tools it needs. Read actions run freely; destructive actions wait for a human (Day 9).
- **Bounded consumption.** Loop limits and token caps, so an injected "repeat forever" costs little (the budget itself lands on Day 8).

**Credentials and the confused deputy.** An agent holding a long-lived admin token lends its authority to anyone who can steer it. Token exchange (RFC 8693) removes that: the agent holds only its own identity, asks a broker for a token per tool call, and receives one scoped to one audience, one resource and one permission, valid for minutes. Each tool checks audience, scope and expiry before it runs, and every exchange is an audit record.

## Build

Blueprint first. The threat list follows the OWASP Top 10 for LLM applications (prompt injection, improper output handling, excessive agency, unbounded consumption). Token exchange follows RFC 8693, implemented with PyJWT (MIT). Policy is plain Python in the harness: a policy engine such as Open Policy Agent (Apache-2.0) adds a server and a rule language for a handful of rules, so it is considered and rejected unless the rule count grows. Each control is a harness component behind a port; FindyFixy implements the ports (policy 4).

### 1. Versioned data

Corpus v2 and golden v2 sit next to v1, which stays frozen. v2 adds no-precedent alerts, conflicting signals, cascades, raw noisy alert text, and 5 incidents whose remediation text carries an injected instruction. Golden v2 adds cases that should escalate and cases whose correct action is destructive. Ingestion keeps both versions apart. Proof that v1 is untouched: the v1 gate run is identical case by case to the last attested run.

### 2. A computed escalation signal

Candidate signals, each computed from recorded values: the reranker's top score, agreement between the answer's severity and the recalled incidents, and whether validation needed a retry. The bar is written before the run: on golden v2, the signal must send to the large model a set share of the cases the judge scores low, at an escalation rate the learner sets in advance. The rule stays a pure function of recorded values, testable without a model (ADR 0001, policy 3). The report states the new escalation rate against v1's 0%, and what the large model changed on the escalated cases.

### 3. Action contract and policy checkpoint

The app declares its actions and their classes through the harness's action port: read (logs, metrics, deploys), reversible (page a human), destructive (roll back a deploy). The triage record gains an action type from that closed set. The policy checkpoint after the model decides:

- A read action passes.
- A rollback passes only with severity sev1 or sev2 and a deploy found in the deploy log within the last 2 hours; otherwise it is downgraded to paging a human.
- Anything outside the declared actions is rejected.

Every decision is a trace event with its reason. Nothing executes yet: the destructive tier waits for Day 9's approval.

### 4. Credential broker

A harness component issues a token per tool call: audience is the tool, scope is the resource with a read permission, expiry 5 minutes, signed with a key from the environment. Each tool verifies audience, scope and expiry before it runs. The `pyjwt` line in `override-dependencies` is removed first (see `code/CHANGELOG.md`, "Decisions for later days"), then `make audit`.

### 5. Injection suite

15 attack prompts (direct injection, role-play, encoded instructions, requests for the system prompt) and the 5 poisoned incidents from step 1, run through the policy checkpoint. In CI the suite runs with a fake model that proposes the attacker's action every time, so the test proves the boundary holds even when the model is fully fooled. One live run shows what the real model proposes.

### 6. Visualizer and artifacts

The Policy box turns built, and the broker appears in the harness lane. ADR 0008 records the phase and reports against the strategy: which policies it applied and any evidence against them. The strategy's enforcement table moves two rows to built. READMEs, CHANGELOG, tracker and ADR snapshot updated in the same commits.

### Packages

`pyjwt` (MIT, maintained, among the most downloaded packages on PyPI). The release cooldown moves forward to about 7 days before the day, then `make audit`.
