# Day 9. Operation

**Outcome:** the fourth transition of `code/docs/strategy.md`. The agent runs as a service. A destructive action pauses until a human approves it, and approving twice executes once. A scheduled evaluation measures quality in operation and raises an alert when it falls below the gate. Two invariants move from planned to built: no destructive action runs without a human or earned autonomy, and quality is measured in operation, not only before release.

## Concept (25 min)

**In the loop or on the loop.** In the loop, a person approves every step: safe, and it does not scale, because the person becomes the throughput limit and starts rubber-stamping. On the loop, the system acts inside a policy, a person approves only the destructive tier, and everything else is observable after the fact. The tier boundary is drawn by reversibility and blast radius: reading logs is free to undo, a rollback in production is not.

**Durable execution.** An approval can take minutes or hours, and the process that started the run may restart in between. So the run's state cannot live in memory. A checkpointer writes the state to Postgres after every step; an interrupt before the execute step stops the run and persists it, and resuming continues from exactly that point, in any process. Resume implies replay, so an external action needs an idempotency key: approving twice must not roll back twice.

**Drift has three sources, and they look alike from outside.** The model changes behind the same name, the data changes (new services, new failure modes, a stale index), or the prompts and code change. A scheduled evaluation on a fixed golden set catches all three, because it holds the questions constant while everything else moves. Operational signals catch drift earlier: escalation rate, validation-failure rate and judge scores on sampled live traffic.

**The promotion path.** The eval gate in CI catches regressions on known cases. Shadow runs a candidate on live traffic and discards its output, catching failures on real inputs at no user impact, at double the inference cost while it runs. Canary serves a small slice of real users. Rollout follows, with rollback as a configuration flip, not a deploy.

**Containers and the model host.** The application ships as a container: multi-stage build, non-root user, pinned base image. The model server stays where the accelerator is: Docker on a Mac cannot reach the Apple GPU, so Ollama runs on the host and containers call it over the network.

## Build

Blueprint first: LangGraph's Postgres checkpointer and interrupt for durable approval, FastAPI (MIT) for the service and Streamlit (Apache-2.0) for the demo screen, all in the bill of materials. An approval SDK such as HumanLayer's is checked first; it is adopted only if it runs without a hosted service. The harness gains an approval port; the service implements it.

### 1. Service

The `uvicorn` line in `override-dependencies` is removed first (see `code/CHANGELOG.md`, "Decisions for later days"), then `make audit`. A FastAPI service in FindyFixy: start a run, read its status, approve or reject a paused run. When policy allows a destructive action, the run pauses with status awaiting approval. Approval is a record (who, when, which action) that the harness checks before the action executes, and the action carries an idempotency key.

### 2. Container

A multi-stage, non-root image for the service, added to the compose file next to the database. Ollama stays on the host; the container reaches it at the host address, tested from inside the container. Every image pinned by digest and scanned before first use. The image installs CPU-only PyTorch wheels for Linux through a uv source with a platform marker, which removes about 3 GB of unused GPU libraries (`code/CHANGELOG.md`, "Open items"); the image size is measured before and after, and the new index passes the supply-chain check.

### 3. Scheduled evaluation

A scheduled job runs the gate, compares the report with the last one, and writes a drift report that flags any measure below its floor and any rise in the escalation rate, each stated against the previous run. A run below the gate raises an alert. The schedule file is generated at setup and git-ignored; only a template is committed.

### 4. Shadow mode

A candidate prompt runs alongside the current one on each request. Both results land in the traces with a variant tag; only the current one is returned.

### 5. Demo screen

A Streamlit page that calls the service: an incident box, the triage result with the model used, the recalled incidents, Approve and Reject when a run is waiting, and a link to the run's trace.

### 6. Visualizer and artifacts

The Human review box turns built. ADR 0010 records the phase and reports against the strategy. The strategy's approval and in-operation rows move to built. READMEs, CHANGELOG, tracker and ADR snapshot updated in the same commits.
