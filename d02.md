# Day 2. Structured output and tools

**Outcome:** the agent emits schema-validated triage records and calls tools. You measure what MCP costs against a direct API call.

## Concept (25 min)

**Structured output is the contract** between a probabilistic component and a deterministic system. Free text cannot be routed, tested or audited. A schema turns each answer into a record with typed fields, and every downstream decision reads fields, not prose.

**Three ways to get it, in rising order of reliability.**

- **Prompt and parse.** Ask for JSON, parse the reply. Fails on stray prose, trailing commas, truncation.
- **JSON mode.** The runtime guarantees syntactically valid JSON. It does not guarantee your shape.
- **Constrained decoding.** The runtime compiles your JSON Schema into a grammar and masks every token that would break it during sampling. Ollama does this when you pass a schema. Shape is guaranteed: keys, types, enums.

Constrained decoding guarantees syntax, not meaning. You saw this on Day 1: the schema said a number, the model wrote 75 on a 0 to 1 field, and nothing stopped it. Numeric bounds and cross-field rules are not reliably enforced by the grammar. So validate semantics in code (Pydantic), feed the validation error back once, then escalate. Bound the retries, or a stubborn model becomes a cost leak.

**Enums are routing.** A `Literal["sev1", "sev2", "sev3", "sev4"]` field is a routing key. Free-text severity is a classification problem you pushed downstream.

**Tool calling.** The model never executes anything. It emits a structured request: a tool name and arguments. Your code validates the arguments, executes the call, and appends the result to the context. The loop repeats until the model answers. The arguments are untrusted input from a model that has read untrusted text. Validate them like any request from the internet. The model never holds credentials; your code does (Day 7).

**MCP.** The Model Context Protocol is JSON-RPC between a client (the agent host) and a server (the tool provider). The client calls `tools/list` to discover tools and `tools/call` to invoke one, over stdio or HTTP. Its value is reuse: one server, many clients, a shared ecosystem.

Its costs are concrete. Every tool's name, description and JSON Schema is placed in the model's context on every turn, so input tokens grow with the number of tools exposed. Tool-selection accuracy also drops as the list grows. A server hop adds latency and another process to run, patch and authenticate.

**The rule you can defend.** MCP where cross-client reuse matters and the tool set is small. Direct function binding on hot paths, exposing only the tool that node needs. Decide by measured tokens and latency per call, which is today's lab.

## Lab (90 min)

### 1. Triage schema

```python
from pydantic import BaseModel, Field
from typing import Literal

class Triage(BaseModel):
    severity: Literal["sev1", "sev2", "sev3", "sev4"]
    component: str = Field(description="service or subsystem most likely at fault")
    next_action: str = Field(description="one concrete first step")
    confidence: float = Field(ge=0, le=1)
```

Swap Day 1's schema for `Triage`. Add a validation-retry: on `ValidationError`, re-ask once with the error text, then escalate.

### 2. Two tools, two ways

Build a fake `get_recent_deploys(service, hours)` that returns JSON from a local file.

- **Direct:** bind it with `llm.bind_tools([get_recent_deploys])` in a LangGraph `ToolNode`.
- **MCP:** wrap the same function in a minimal MCP server (`uv add mcp`, FastMCP) and connect with `langchain-mcp-adapters`. Ask Claude Code to scaffold both.

### 3. Measure

For 10 runs of each path, log input tokens, output tokens and wall time. Put the result in `notes/day2.md` as a table.
